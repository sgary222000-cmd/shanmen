## 1. 核心玩法理解

### 1.1 一句話

玩家接手一座沒落宗門，以「一個遊戲月」為單位安排生產、建設、弟子與掌門行程，讓宗門與主角互相拉抬：宗門供應主角突破所需，主角替宗門取得更高階資源與生存空間；長期目標是讓宗門在掌門閉關、壽終、飛升後仍能自主運作並延續數代。

### 1.2 核心循環【已確認】

```
安排工作與主角行程 → 預覽本月收支 → 推進一月
  → 結算（維護 → 生產/建造 → 修煉 → 派遣/戰鬥/探索 → 電腦宗門 → 事件/月報/自動存檔）
  → 處理事件 → 建設、培養、交易、探索 → 再次安排
```

- 時間只在玩家按下「推進月份」時前進；沒有現實倒數，關閉遊戲世界不會變化。
- 主角每月只有一項「主要行程」（閉關、授課、探索、煉丹…），下達宗門命令不佔行程。
- 外門弟子是「群體」（人數 + 分工），內門以上才是具名、逐人養成的角色。
- 戰鬥是自動回合制，玩家只配置隊伍、站位、功法、消耗品與策略規則。
- 秘境第一次是節點式探索（親自走路線、選分岔），完成後可改為派遣（收益較低、耗月份與補給）。

### 1.3 已確認需求清單

| 類別 | 內容 |
|---|---|
| 類型 | 大型單機修仙宗門經營，長期慢玩、多目標沙盒，無現實倒數 |
| 成長 | 主角與宗門共同成長；繼承衰敗宗門開局 |
| 經營 | 區域式建設；適中深度的產業與人員管理 |
| 人物 | 主角行程制；外門群體、內門與親傳個別養成；資質與培養並重 |
| 傳承 | 開局自選主傳承，之後發展分支 |
| 戰鬥/探索 | 自動回合戰鬥；首次秘境節點探索、完成後派遣 |
| 世界 | 電腦宗門（本機規則，不用付費 AI）；前期有限衝突，後期聯盟、吞併、滅宗 |
| 長線 | 完整九大境界；飛升後雙界經營 |
| 表現 | 精緻插圖、無須動畫 |
| 優先序 | 宗門經營 > 勢力競爭 > 探索冒險 > 人物劇情 |
| 開發要求（啟動指令） | 電腦瀏覽器優先；主動月份推進；可延續存檔；規則/資料/介面/素材分開；未完成內容清楚標示；臨時圖不冒充正式素材；保護存檔並規劃遷移；每項功能驗證並更新進度；不宣稱未驗證的時數或完成度；依里程碑逐步做，不一次做完所有境界、美術與雙界 |

企畫書中「推薦方案」（Claude Code 開發、瀏覽器優先、本機存檔、工筆重彩 + 青綠山水）與技術選型（TypeScript、React、Vite、IndexedDB）屬推薦，我在第 3 節說明是否採用。

## 2. 規則矛盾、P0 必須補齊的規則與製作風險

### 2.1 規則矛盾或互相拉扯之處

| # | 位置 | 問題 | 【Claude 建議】 |
|---|---|---|---|

| C3 | §18 P0「開局先完成劍修」vs §14 引導任務「建立穩定丹藥供應」、§10「開局選擇不得讓你失去核心生活功能」 | 劍修開局也必須能煉丹，否則無法築基與完成引導。 | 煉丹房與基礎丹方屬於「宗門通用」功能，不屬於丹道；丹道只給加成與進階丹方。 |
| C4 | §3 結算順序第 5 步「結算已確認的探索結果」vs §12 首次節點探索 | 節點探索需要玩家當場選路，但結算順序把探索放在推進月份之中，兩者時機不一致。 | 首次探索在「安排階段」當場遊玩，進入時鎖定隨機種子並佔用主角與隊員本月行程；獎勵先記為「待入庫」，在推進月份第 5 步正式入帳。派遣（P1）才完全在結算內處理。 |
| C5 | §3 第 3 步「同月產出不得充當其他生產投入」 | 原則合理（防止一月內跑完整條產業鏈），但未說明：建造完成當月是否生產、當月收成的糧食能否供當月食用。 | 本月完成的建築**下月**開始運作；所有消耗只扣「月初庫存」，本月產出一律下月才能用。介面在預覽中直接顯示這點。 |
| C6 | §11 五人隊伍 vs §14 開局「有限外門弟子」、引導只招一位內門 | P0 前期可能湊不滿五個具名角色；外門是群體，能否上場未定義。 | 隊伍**最多**五人、可少於五人；P0 只有主角與具名內門可上場，外門不參戰。秘境首戰按「主角 + 1～2 名內門」設計難度。 |
| C7 | §11「隨機使用可保存的種子，避免讀檔重擲」vs §17「多個手動存檔欄位」 | 只要能讀舊檔，玩家就能回到之前換一條路；種子只能防止「同一狀態重開畫面就換結果」。 | 明確定義目標：**同一存檔 + 同一操作 → 同一結果**；不嘗試阻止讀舊檔。這已足夠滿足 P0 驗收「無法僅靠重開畫面領取重複獎勵」。 |
| C8 | §5「每月一項主要行程」vs「閉關可預設多月並允許中斷」 | 閉關期間若發生需要主角親自處理的事件（探索、迎敵），規則未定。 | 閉關中仍可下達宗門命令；若要改做其他行程必須先「中斷閉關」，中斷代價（例如損失本次累積的閉關加成）在開始閉關前顯示。 |

### 2.2 P0 必須補齊的規則（企畫書未定義），附具體預設值

以下全部是【Claude 建議】的暫定值，會集中記錄在 `docs/暫定數值與決策.md`，並在遊戲內數值旁標示「暫定」。數值目的只是讓 P0 能完整跑一輪，平衡會在試玩後調整。

**時間與開局**

| 項目 | 建議預設 |
|---|---|
| 開局時間 | 第 1 年 1 月；主角 18 歲、煉氣一層 |
| 開局物資 | 靈石 300、糧食 200、石材 80、靈木 60、藥草 20、丹藥 0 |
| 開局人員 | 外門弟子 12 人（群體）、具名內門 0 人 |
| 開局建築 | 宗門大殿（殘破，Lv0，需修復）、弟子居所 Lv1，其餘空槽 |
| 主峰槽位 | 8 格 |
| 新手保護 | P0 沒有電腦宗門攻擊，因此保護期暫不需要；P1 起訂為前 36 個月 |

**P0 五種建築**

| 建築 | 作用 | Lv1 建造 | 每月維護 | 升級 |
|---|---|---|---|---|
| 宗門大殿 | 解鎖招募、決定建築上限等級 | 修復：石材 40、靈木 30、靈石 50、2 個月 | 靈石 5 | Lv2：提升招募人數與其他建築上限 |
| 弟子居所 | 外門容量 | 已存在 | 糧食依人數 | Lv2：容量 +10 |
| 靈田 | 產糧食與藥草（可切換作物） | 石材 10、靈木 20、1 個月 | — | Lv2：產量與工位增加 |
| 煉丹房 | 以藥草 + 靈石煉丹（P0 兩種丹方） | 石材 30、靈木 20、靈石 60、2 個月 | 靈石 5 | Lv2：成功率、可同時煉兩爐 |
| 聚靈陣 | 提高主峰靈氣容量（修煉與突破用） | 石材 30、靈石 100、2 個月 | 靈石 10 | Lv2：容量再提升 |

以上五種改用「倉庫」或「藏經閣」替換也可以，我選聚靈陣是因為 P0 需要讓「靈氣環境」實際影響修煉與突破。

**資源與產出**

- P0 資源：靈石、糧食、石材、靈木、藥草、丹藥（分品項）、靈氣（區域容量，不是可累積的庫存）。靈礦、法器、符籙 P1 再加入。
- 所有數值以**整數**儲存（避免小數累積誤差）；機率以萬分比儲存。
- 外門分工：耕作、採集（石材/靈木）、雜務、修煉。每人每月固定產量；未分工者視為修煉。
- 糧食：外門每人每月 1；內門 0.5（取整進位）；築基以上 0。糧食不足時：先停止「修煉」分工的修煉收益，連續兩個月不足則外門滿意度下降並有人離開（有預警），不會死人。
- 缺錢缺料：建築維護不足時該建築停用，不扣成負數；P0 提供一個「下山接委託」的外門分工，固定換取少量靈石，作為一定能翻身的保底收入，避免死局。

**修煉與突破**

- 煉氣分九層（企畫提案），築基分前、中、後、圓滿。
- 每月修為 = 基礎值 × 靈根係數 × 靈氣係數 × 行程係數（閉關 1.5、其他行程 0.3～0.5）。
- 煉氣小層：修為滿即自動晉層，不需材料、不會失敗。
- 煉氣九層 → 築基：需修為滿、築基丹 1 顆、靈氣環境達標；成功率基礎 60%，聚靈陣與丹藥品質可提高，上限 90%。失敗：受傷 3 個月 + 損失 30% 修為，**不會死亡**（P0 不實作死亡）。
- 突破由玩家主動選擇「本月行程：突破」，結算時判定；畫面事前顯示機率、影響因素與失敗代價。

**招募與弟子**

- 大殿修復後每 6 個月一次「山門招生」：外門 +3～6 人；並提供 3 名內門候選人讓玩家比較，最多選 1 名（需聲望或靈石）。
- 外門晉升內門：從外門群體中「選拔」，生成一名具名角色，外門人數 −1。
- 具名角色欄位（P0）：ID、姓名、性別、年齡、境界、修為、靈根（金木水火土組合 + 品級）、健康、忠誠、技藝（煉丹/耕作/戰鬥）、裝備（P0 先空）、目前行程。性格、關係、職位 P1。
- 姓名由本機姓氏/名字字庫組合；肖像使用標示「臨時」的佔位圖。

**戰鬥**

- 屬性：生命、攻擊、防禦、速度、命中、抗性 + 靈力（技能資源）。
- 行動順序：速度高者先；平手比 ID（穩定規則）。
- 傷害：`max(1, 攻擊 × 技能倍率 − 防禦)`，命中/閃避以命中 − 抗性換算機率，均用存檔中的隨機狀態。
- 回合上限 30；到上限判定「平局」= 我方撤退，不給首領獎勵，不算失敗死亡。
- 失敗：參戰者受傷（健康下降、數月療傷），可繼續遊戲。
- P0 策略：預設策略 + 兩個開關（生命低於 X% 時用丹藥、優先攻擊生命最低者）。

**探索（P0 一個秘境：「荒廢洞府」）**

- 約 6～8 個節點：入口 → 分岔（兩條路）→ 資源/事件/敵人 → 首領 → 出口。
- 可在任何非戰鬥節點撤退，帶回已取得物資的 50%（事前顯示）。
- 首領首次擊破獎勵為「築基丹丹方」（開局只會煉聚氣丹，讓探索成為築基的前置），全存檔唯一，記錄在存檔的「已領取獎勵」清單中。
- 完成後可重入，但節點資源減少、無首次獎勵；正式「派遣」系統放在 P1。

### 2.4 製作風險

| 風險 | 說明 | 對策 |
|---|---|---|
| 範圍極大 | 九大境界、雙界、19 種建築、6～8 個勢力，內容量遠超一般獨立遊戲 | 嚴格依 P0→P4 推進；每階段先做「可玩完的薄切片」 |

| 操作疲勞 | 長期慢玩若每月要點很多下會很煩 | P0 起記錄「每月必要點擊數」；P1 加入連續推進與工作範本 |

## 3. 技術選型、專案結構、存檔與啟動方式

### 3.1 目前環境檢查結果

- 我的雲端工作環境：Node.js 22、npm 10、git 2.43 可用，可正常下載 npm 套件。
- 專案資料夾 `/mnt/project-files`：原本是空的，現在有 `docs/`（企畫書）與 `review/`（本文件）。
- 專案**沒有連結任何 GitHub repo**，目前沒有程式碼。

### 3.2 技術選型【Claude 建議，採用企畫書推薦並補充】

| 用途 | 選擇 | 理由 |
|---|---|---|
| 語言 | TypeScript（嚴格模式） | 大量資料定義與存檔結構，型別能及早抓錯 |
| 畫面 | React 18 | 列表、表單、面板多，元件化合適；遊戲沒有動畫，不需要遊戲引擎 |
| 建置 | Vite | 啟動快、輸出純靜態檔，可直接放上靜態網站 |
| 狀態 | 遊戲引擎是純 TypeScript（不依賴 React）；畫面用輕量 store（Zustand）訂閱 | 確保「畫面重繪不改變世界狀態」，也讓模擬器能不開畫面直接跑 |
| 存檔 | IndexedDB（透過 `idb` 小型套件）+ JSON 匯出/匯入 | 容量足夠、瀏覽器原生 |
| 驗證 | Zod（存檔與內容資料格式驗證） | 匯入前驗證、內容資料打錯 ID 時立即報錯 |
| 測試 | Vitest（引擎單元測試）+ Playwright（實際開瀏覽器跑 P0 流程） | 對應驗收標準的自動檢查 |
| 亂數 | 自行實作小型可序列化 PRNG（例如 xoshiro128**） | 狀態可存進存檔，讀檔後結果一致 |

不使用後端、帳號、付費 API。

### 3.3 檔案結構【Claude 建議】

```
shanmen/                         專案根目錄
├─ docs/                         企畫書、進度、決策、暫定數值、素材清單
├─ src/
│  ├─ engine/                    純規則，不 import React
│  │  ├─ state/                  世界狀態型別與建立新遊戲
│  │  ├─ commands/               玩家指令（指派、建造、行程…）＋合法性檢查
│  │  ├─ systems/                各系統，一個資料夾一個
│  │  │  ├─ time/                月結算流程（依 §3 的 7 步驟）
│  │  │  ├─ economy/             資源、維護、生產
│  │  │  ├─ buildings/
│  │  │  ├─ characters/          主角、外門群體、具名弟子、招募
│  │  │  ├─ cultivation/         修為、突破
│  │  │  ├─ combat/
│  │  │  ├─ exploration/
│  │  │  ├─ events/
│  │  │  └─ factions/            （P1 起）
│  │  ├─ rng/                    可序列化亂數
│  │  └─ index.ts                對外介面：newGame / applyCommand / previewMonth / advanceMonth
│  ├─ content/                   內容資料（不含邏輯），每類一個資料夾
│  │  ├─ buildings/ recipes/ realms/ techniques/ enemies/ realms-secret/ events/ names/
│  │  └─ registry.ts             載入並以 Zod 驗證所有內容，檢查 ID 唯一與引用正確
│  ├─ save/                      存檔格式、遷移、IndexedDB、匯出匯入
│  │  ├─ schema/ migrations/ storage.ts
│  ├─ ui/                        React 畫面；只讀狀態、只送指令
│  │  ├─ pages/ components/ theme/
│  └─ dev/                       開發測試工具（只在開發模式載入，與玩家介面分開）
├─ assets/
│  ├─ placeholder/               臨時圖，檔名與畫面上都標示「臨時」
│  └─ final/                     正式素材（P0 為空）
├─ tools/simulate.ts             無畫面模擬器：自動玩 N 年並輸出指標
└─ tests/                        引擎測試、存檔往返測試、瀏覽器流程測試
```

關鍵原則：

1. **引擎是純函式**：`advanceMonth(state, content) → { state, report }`，同樣輸入一定同樣輸出。畫面只能透過 `applyCommand` 改變狀態。
2. **內容用穩定 ID**：如 `building.alchemy_room`、`recipe.qi_pill`。存檔只存 ID 不存內容本身，所以改數值不需要改存檔；刪除或改名 ID 才需要遷移。
3. **一個檔案只做一件事**，避免巨大單檔；每個系統可獨立測試。

### 3.4 存檔方案【Claude 建議，依企畫書 §17 落實】

**存檔內容**

```
SaveFile {
  format: "shanmen-save"
  formatVersion: 1            每次結構變更 +1
  gameVersion: "0.1.0"
  saveId, slot, createdAt, updatedAt
  summary { 宗門名, 主角名, 境界, 遊戲年月 }   讀檔列表顯示用，不必解開全部資料
  checksum                    偵測檔案損壞
  world {
    date { year, month }
    resources, buildings, characters, outerDisciples,
    protagonist, schedules, explorations, claimedRewards,
    events, reports(只保留最近 N 個月), factions(P1),
    rng { 各類亂數的狀態 }
    nextIds                   產生新 ID 的計數器
  }
}
```

**欄位與輪替**

- 自動存檔：每次推進月份後寫入，**三個自動欄位輪替**（最新的覆蓋最舊的）。
- 手動存檔：8 個欄位。
- 寫入方式：先完整寫入新資料並驗證，成功後才標記為最新，寫到一半斷電不會毀掉舊檔。
- 啟動時呼叫瀏覽器「持久儲存」請求，降低被瀏覽器自動清除的機會。

**匯出與匯入**

- 匯出：下載一個 `.json` 存檔檔案（可存到雲端硬碟備份）。
- 匯入：先驗證格式與版本、顯示摘要，**一律放進新欄位或由玩家選擇空欄位**，不直接覆蓋現有好檔。

**升版遷移**

- `migrations/` 內一個版本一支遷移函式（v1→v2、v2→v3…），讀到舊版存檔時依序執行。
- 遷移前自動把原檔另存為「升版前備份」。
- 每次版本變更都附「舊檔遷移測試」：用前一版的範例存檔跑遷移並驗證。

**防重複獎勵**

- 隨機狀態在存檔裡，畫面重開不會換結果。
- 唯一獎勵記錄在 `claimedRewards`，領過就不能再領。
- 月份推進時先寫入「本月已結算」標記，事件未處理前不可再推進。

### 3.5 程式碼放哪裡與版本保存【需要你決定】

目前專案沒有 GitHub repo。我的雲端環境每次工作結束就會清空，所以程式必須存到別的地方。兩個選擇：

1. **建立 GitHub repo（建議）**：有完整版本紀錄、每次修改都能還原，也能用 GitHub Pages 免費放上網，你直接用瀏覽器開網址就能玩，**電腦不必安裝任何東西**。需要你建立一個 repo（可設私人）並連結到這個專案。
2. **只存在專案資料夾**：程式放在 `/mnt/project-files/game/`，資料夾內用 git 保存版本，每個里程碑打包一份 zip。可以運作，但你要在自己電腦玩就得安裝 Node.js（見第 5 節）。

### 3.6 啟動方式【Claude 建議】

| 對象 | 方式 |
|---|---|
| 你（玩家/驗收） | 方案 1：開啟 GitHub Pages 網址即可。方案 2：下載 zip，安裝 Node.js 後在資料夾執行 `npm install`、`npm run dev`，瀏覽器開啟顯示的網址 |
| 我（開發驗證） | 在雲端環境啟動開發伺服器，用 Playwright 實際操作瀏覽器、截圖，並附上結果 |

企畫書已說明「不能承諾雙擊檔案即可運作」，這是因為瀏覽器對本機檔案有安全限制；GitHub Pages 是最接近「點開就玩」的做法。另外提醒：網址一旦固定就不要再換，否則瀏覽器內的存檔會看不到（仍可透過匯出檔搬過去）。

P0 目標（啟動指令）：能實際玩完「建立宗門 → 安排工作與修煉 → 推進月份 → 生產資源 → 升級建築 → 培養弟子 → 探索與戰鬥 → 存檔 → 關閉並重新載入」，並附實際驗證結果。

每項任務完成時：執行對應測試、更新 `docs/開發進度.md`、記錄問題與啟動方式。

| 編號 | 任務 | 內容 | 驗收方式 |
|---|---|---|---|
